# AGENTS.md — ips-frontend

Инструкции для работы в `services/ips-frontend`. Пути ниже относительны этому каталогу. Общая архитектура, запуск стека и известные ошибки — в [README](../../README.md).

---

## Обзор проекта

Пользовательский UI учебного симулятора: мониторинг состояния, настройки порогов, сценарии телеметрии и журнал тревог. Элементы болюса показаны в интерфейсе, но кнопка введения пока является заглушкой; не описывайте её как завершённую интеграцию. Админ-панель — отдельный сервис `../ips-admin-frontend`, не раздел этого приложения.

**Стек технологий:**
- React 19.2 + TypeScript 6.0
- Vite 8.2 (сборщик и dev-сервер)
- Tailwind CSS **v4** (CSS-first конфиг через `@theme`, НЕ v3)
- React Router 7 (клиентская маршрутизация)
- Axios (HTTP-клиент)
- Oxlint (линтер, конфигурация `.oxlintrc.json`; не ESLint)
- Бэкенд: FastAPI в соседнем сервисе монорепозитория; прокси Vite локально и nginx в Docker

Версии фиксирует `package-lock.json`, декларации — `package.json`. Для разработки рекомендуется Node.js 24 LTS и npm, как в Docker builder (`node:24-alpine`). Технический минимум Vite — 20.19+ в ветке 20 либо 22.12+, но Node.js 20 уже не поддерживается. `strict` сейчас **не включён**; `noUnusedLocals`, `noUnusedParameters` и `noFallthroughCasesInSwitch` включены. `erasableSyntaxOnly: false` нужен для существующих `enum` — не включайте его без согласованной замены enum.

## Команды разработки

```bash
# Из корня репозитория
cd services/ips-frontend

# Воспроизводимая установка по lock-файлу
npm ci

# Запуск dev-сервера (порт 5173, proxy на бэкенд 8000)
npm run dev

# Production-сборка
npm run build

# Предпросмотр production-сборки
npm run preview

# Линтинг
npm run lint
```

**Dev-сервер:** `http://localhost:5173`, проксирует `/api/*` на `http://127.0.0.1:8000` (см. `vite.config.ts`). Явный IPv4-адрес совместим с loopback-публикацией backend в Compose.

**Бэкенд и генератор** запускаются отдельно (см. соответствующие проекты).

`npm run build` выполняет `tsc -b && vite build` и создаёт `dist/`; `npm run lint` не заменяет проверку TypeScript. Скрипта `npm test` и проектных UI-тестов пока нет. `npm run preview` — предпросмотр сборки, не проверка production-конфига nginx.

Docker-стек на VDS из корня: `docker compose up --build -d --wait` после настройки DNS и TCP 80/443 по README. UI доступен на **`https://ips.alexgallax-edu.ru`** через Caddy; собственный порт хоста у frontend не публикуется, внутри nginx слушает **8080**. Runtime-образ — `nginxinc/nginx-unprivileged:1.30-alpine`, master и workers работают через `USER nginx`, не root. Полный `nginx.conf` копируется в **`/etc/nginx/nginx.conf`**, не в `conf.d/default.conf`: он сам задаёт PID и все временные пути в `/tmp`, логи направляет в stdout/stderr. Не возвращайте `user nginx;` и PID в `/var/run` в этот конфиг.

Backend-цель — `backend:8000`; healthcheck использует `http://127.0.0.1:8080/health` с таймаутом 3 с. Проверка конфигурации: `docker compose exec -T frontend nginx -t`. Builder копирует явно HTML, Vite/TypeScript-конфигурации, `src/` и `public/`, не весь каталог. Если появится новый необходимый сборке файл, добавьте его в `COPY`; конфигурация nginx копируется только в runtime-стадию.

Compose публикует прямые API и диагностический порт админки только на `127.0.0.1`, а публичные UI, Swagger и API предоставляет через HTTPS Caddy без авторизации. Общий блок `x-app-options` добавляет `no-new-privileges:true`, `cap_drop: [ALL]` и ротацию Docker-логов (`local`, `max-size: 10m`, `max-file: 3`). Не удаляйте его наследование.

Caddy направляет `/docs`, `/docs/*`, `/redoc`, `/openapi.json` основного домена прямо в backend; остальные пути — в этот nginx. Сохраняйте `map $http_x_forwarded_proto $upstream_scheme` и передачу `X-Forwarded-Proto`, иначе FastAPI потеряет HTTPS-схему. Для локального Vite-запуска Caddy не нужен. `FRONTEND_PORT` больше не используется; внешний HTTP/HTTPS-порт задаётся для Caddy.

## Архитектурные соглашения

### 1. Стили — `src/index.css` и существующие utility-классы

Новые дизайн-токены и переиспользуемые компонентные стили добавляйте в `src/index.css`, без отдельных CSS-модулей. В текущих JSX уже есть Tailwind utility-классы и inline-стили, в том числе динамические. Это не означает, что статичные стили нового блока следует размазывать по компонентам. Исторический `src/App.css` не используется.

Структура `index.css`:
- `@theme { ... }` — дизайн-токены (цвета `--color-pump-*`, шрифты, анимации)
- `@layer components { ... }` — все переиспользуемые классы
- Для новых кастомных классов используйте **префиксы**: `pump-*`, `settings-*`, `alerts-*`, `scenario-*`, `dev-*`, `nav-*`

**При добавлении нового блока** создавайте для него отдельную секцию с префиксом в `@layer components`.

### 2. Tailwind CSS v4 — синтаксис

Это **Tailwind v4**, а не v3. Конфигурация делается в CSS, а не в `tailwind.config.js`.

✅ Правильно (v4):
```css
@theme {
  --color-pump-green: #10b981;
}
.pump-card {
  @apply bg-pump-surface rounded-2xl;
}
```

❌ Неправильно (v3-стиль, не работает):
```css
.pump-card {
  @apply bg-pump-green-500;  /* Такого цвета нет */
}
```

### 3. API-слой

Все запросы к бэкенду — **только через `src/services/api/api.ts`**. Компоненты и хуки не должны напрямую импортировать axios или `client.ts`.

Каждая функция API:
- Использует `getPumpId()` из `config/pump.ts` для формирования URL
- Возвращает типизированный ответ (`Promise<T>`)
- Обрабатывает не-2xx ответы бэкенда (особенно 403 — см. `saveSettings`, `resetPumpBlock`)

### 4. Управление `pump_id`

`pump_id` хранится в `localStorage` под ключом `ips_pump_id`. Все API-запросы автоматически подставляют текущий `pump_id` в URL.

При изменении `pump_id` диспатчится `CustomEvent('pump-id-changed')`, уведомляющий подписчиков о новом идентификаторе. Не все подписчики выполняют периодический polling:

`usePumpState` перезапускает polling; `usePumpSettings` и `useTelemetryScenarios` загружают данные заново; `AlertsContext` сбрасывает список и счётчик, а затем использует следующий такт опроса. `usePumpId` управляет черновиком и кнопкой применения ID в заголовке.

Не создавайте второй источник выбора помпы в компонентах. В текущем `getPumpId()` URL-параметр `?pump=...` имеет приоритет **при каждом вызове**, не только при первом визите; переключение через поле при таком URL не работает надёжно. Старые запросы также не отменяются при смене ID. Если задача касается переключения, проверяйте привязку ответа к исходной помпе, отмену/игнорирование устаревших ответов и кодирование ID в URL.

### 5. Polling

Два независимых polling-а:
- `usePumpState` — для Dashboard (глюкоза, болюс, базал)
- `AlertsContext` — для отслеживания `alerts_count` и обновления списка тревог

Оба используют `POLLING_INTERVAL_MS` из `config/polling.ts` (по умолчанию 3 секунды).

У `usePumpState` задержка после ошибки линейная: `ERROR_RETRY_DELAY_MS × число ошибок` (база 2000 мс). `MAX_ERROR_RETRIES=5` объявлен в конфиге, но этот хук его сейчас не использует и после пяти ошибок не останавливается. `AlertsContext` имеет свой независимый опрос; переключатель `POLLING_ENABLED` из хука Dashboard его не отключает. `useTelemetryScenarios` не имеет периодического polling: загрузка происходит при монтировании, смене помпы и ручном обновлении.

### 6. Состояние болюса

Текущее поведение: после успешного ответа разблокировки (`status: "OK"`) выставляется `bolusStatusOverride=ALLOWED`. Он сбрасывается при `bolus_status === 'allowed'` в ответе backend или при смене помпы. Новое запрещающее состояние само его не сбрасывает — это известный дефект, который может скрыть блокировку.

Кнопка введения в `usePumpState.deliverBolus()` только ждёт 500 мс и вызывает `fetchStatus()`. Функции отправки `POST /bolus/deliver` в API-слое пока нет. Кроме того, `BolusPanel` отключает кнопку только для `blocked`, но не для `suspended`, `pump_off` или неизвестного статуса. Backend также содержит ошибку проверки болюса; исправление только UI не закрывает проблему.

Для новых действий, влияющих на разрешение подачи, не используйте optimistic override как источник истины: результат должен согласовываться с актуальным состоянием backend.

### 7. Мок-данные и актуальность

Константа `MOCK_PUMP_STATE` в `usePumpState.ts` используется **только** при первой ошибке загрузки (когда бэкенд недоступен и данные ещё ни разу не получены). После первой успешной загрузки мок больше не применяется — показываются последние актуальные данные.

Точнее, при первом fallback `hasLoadedRef` тоже становится `true`; последующие ошибки сохраняют тот же мок до успешной загрузки. При смене ID флаг сбрасывается. Мок содержит обязательное `alerts_count: 0`. Ошибка/возраст данных отдельно не показываются: ни мок, ни последнее сохранённое состояние не являются подтверждением текущего состояния сервера.

## Соглашения по коду

### Именование

| Элемент     | Стиль                                                                                                                   |
|-------------|-------------------------------------------------------------------------------------------------------------------------|
| Компоненты  | `PascalCase` (`PumpHeader.tsx`, `GlucoseDisplay.tsx`)                                                                   |
| Хуки        | `camelCase` с префиксом `use` (`usePumpState.ts`)                                                                       |
| Файлы типов | `camelCase` (`types.ts`)                                                                                                |
| Функции API | `camelCase` глагол + существительное (`getPumpStatus`, `resetPumpBlock`)                                                |
| CSS-классы  | `kebab-case` с префиксом блока (`pump-card`, `alert-item`, `scenario-control-btn`)                                      |
| Enum'ы      | `PascalCase` имена типов, `UPPER_SNAKE_CASE` члены, lowercase/snake_case значения (`BolusStatus.PUMP_OFF = 'pump_off'`) |

### Функциональные компоненты

Все компоненты — **функциональные**. Не использовать классы `React.Component`.

### Типизация

- `strict` сейчас не включён; не выдавайте это за строгую проверку всех nullable-состояний и не меняйте режим неявно в несвязанных задачах
- Не использовать `any` — использовать `unknown` с type guards
- Enum-значения должны соответствовать `../ips-backend/src/ips_backend/pump/data/status.py`
- `PumpState` объявляйте один раз; синхронизируйте обязательные поля (включая `alerts_count`) с response-моделью backend и моками
- В браузерных хуках тип таймера — `ReturnType<typeof setTimeout>`, не `NodeJS.Timeout`; `tsconfig.app.json` подключает `vite/client`, а не Node-типы

### Импорты

Сохраняйте принятый порядок импортов (не утверждайте, что он проверяется отсутствующим ESLint):
1. React/сторонние библиотеки
2. Модули `services/`
3. Модули `hooks/`, `context/`
4. Модули `config/`
5. Компоненты
6. Стили (только в `main.tsx`)

## Типичные задачи и решения

### Добавить новое поле в ответ бэкенда

1. Обновить соответствующий интерфейс в `src/services/api/types.ts`
2. Если поле используется в UI — обновить компонент, который его отображает
3. Если поле влияет на логику (например, новое состояние) — обновить `usePumpState.ts`

### Добавить новый эндпоинт бэкенда

1. Добавить типы запроса/ответа в `src/services/api/types.ts`
2. Добавить функцию в `src/services/api/api.ts` (использовать `getPumpId()`)
3. Создать хук или использовать в компоненте напрямую

### Изменить стиль существующего элемента

**Только в `src/index.css`!** Найти класс элемента (через DevTools) и изменить его в соответствующей секции.

### Добавить оптимистичное обновление

Для некритичных UI-данных сначала определите отмену изменения при ошибке, смене помпы и устаревшем ответе. Не копируйте существующий `bolusStatusOverride` в проверки безопасности: сейчас у него нет корректного сброса при новом запрете. Разрешения действий должны подтверждаться сервером; не исправляйте рассинхронизацию backend только оптимистичным отображением.

## Отладка

### Моргание UI

Если компонент моргает при polling:
- Проверить, что массивы/объекты в пропсах не пересоздаются на каждом рендере
- Использовать `useMemo` для мемоизации по содержимому (паттерн из `messages` в `usePumpState`)
- Для списков использовать `React.memo` на компоненте элемента (как `MessageFeed`)

### Запросы идут на старый `pump_id`

Проверьте не только `getPumpId()` и подписку `onPumpIdChange`, но и оставшийся `?pump=...` в URL. Затем проверьте старые незавершённые запросы: изменение ID не отменяет их автоматически.

### Блокировка болюса не снимается сразу

Сравните поля `manual_action_required`, `basal_speed_pc` и `bolus_status` в ответе `/status`, не только label в UI. Backend сейчас сбрасывает лишь первый флаг, а остальные поля пересчитывает при следующей телеметрии; override может скрыть это расхождение. Не рассматривайте его установку как исправление backend.

### 403 от бэкенда при сохранении настроек

Это штатная ситуация — бэкенд валидирует соотношения полей. Хук `usePumpSettings.ts` применяет ответ независимо от статуса (200 или 403) и показывает сообщение только при 403.

Ошибки типов, диапазонов и обязательных полей дают 422 с другим форматом ответа; их нельзя интерпретировать как `SettingsResponse`.

### Не обновляются тревоги

`AlertsContext` перечитывает список при изменении `alerts_count`. После заполнения backend-буфера его длина не меняется, хотя записи заменяются: новая критическая тревога может не появиться в списке. Сам счётчик включает также записи `off`. Для исправления нужен признак версии/последнего события либо независимое обновление списка; не полагайтесь только на длину.

## Тестирование

UI-тесты и скрипт `npm test` не настроены. Выполняйте `npm run lint` и `npm run build`, затем проверяйте вручную:

1. **Бэкенд выключен:** при открытии `/dashboard` должна загрузиться мок-версия состояния
2. **Бэкенд включен:** данные должны подтягиваться с бэкенда, мок не показывается
3. **Смена `pump_id`:** с URL-параметром и без него, при незавершённых запросах — известные дефекты описаны выше, не считайте тест пройденным по смене текста поля
4. **Polling:** открыть DevTools Network — запросы `/status` должны идти каждые 3 секунды
5. **SPA-роутинг:** обновить страницу на `/alerts` — она должна загрузиться без 404
6. **API-прокси:** `/api/v1/pumps/pump-1/status` возвращает JSON, не `index.html`; запросы сценариев доходят до telemetry
7. **Тревоги и запреты:** заполнение буфера, новая критическая запись, повторная блокировка после reset не должны теряться при исправлении этих мест

- ❌ Не использовать `peer-checked:` в `@apply` — в v4 это ломается, используйте обычный CSS-селектор `:checked ~`
- ❌ Не создавать новые файлы стилей (`*.css`, `*.module.css`) — всё в `index.css`
- ❌ Не использовать class-компоненты React
- ❌ Не хардкодить `pump_id` в URL запросов
- ❌ Не обращаться к axios напрямую из компонентов
- ❌ Не использовать `any` вместо проверки неизвестного ответа API
- ❌ Не менять имена, типы и строковые enum-значения API только в одном сервисе; порядок JSON-полей сам по себе контрактом не является
- ❌ Не редактировать вручную `dist/`, `node_modules/` и `.tsbuildinfo`

Enum-значения фронтенда **должны быть lowercase и совпадать 1-в-1** с бэкендом:
```typescript
// ✅ Правильно
export enum GlucoseLevel {
  NORMAL = 'normal',  // совпадает с Python: NORMAL = "normal"
  LOW = 'low',
  HIGH = 'high',
}

// ❌ Неправильно
export enum GlucoseLevel {
  NORMAL = 'NORMAL',  // нарушает контракт и сопоставление статусов с backend
}
```
